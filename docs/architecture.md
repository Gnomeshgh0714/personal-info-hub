# 设计口径

本文记录 personal-info-hub 的设计决策与口径约定。改引擎行为前先读这里；改了口径要同步改本文与回归护栏。

## 数据流

```
sources.json 白名单 → iter_source_files 定点遍历 → 提取器（一文件 → 0..N 条）
  → dedup_key 分配/沿用 id → 内容哈希判重 → 追加 jsonl
  → 同 id 取最后一行聚合 → 六分类视图 + 待核验队列 + 采集日志
```

唯一事实源是 `中台数据/personal_info.jsonl`。视图、队列、日志都是生成物：与 jsonl 不一致时以 jsonl 实时聚合为准，重跑一次采集即刷新。视图不手改、不另存历史副本。

## append-only 事件日志与版本递增

jsonl 是追加式事件日志，不是状态表。同一事实（dedup_key = 分类 + 名称 + 证据路径）的更新以新行落盘、`版本` 递增；下游视图按「同 id 取最后一行」聚合。旧行不删不改，历史靠日志本身回溯。id 首次入库时分配（`PI-` + 四位序号），此后永远沿用，不因重扫而变。

## 内容哈希幂等

`记录哈希` 是内容指纹，计算时排除 id、版本、采集时间、扫描模式、记录哈希本身。哈希与游标里存的一致则重跑不追加新行——这是幂等的依据，也是「重跑不撑肿历史」的保证。场景类字段（简历场景/场景警示/主源裁决）只在非空时落盘：无条件写会让全库每条的哈希都变，重跑平白追加几百行「版本 2」。

## 游标增量

`collector/state/cursor.json` 存文件级签名（mtime + size）、id 映射与记录哈希。默认 `--incremental` 只处理新增/变更文件；`--full` 只清文件签名游标，id 映射与记录哈希保留——所以全量重扫也不会重复追加未变条目，更不会重分配 id。游标不入库（gitignore），换机器后首轮全量重建即可。

## 证据定位：两个层级

- **条目级**（`证据定位`）：整条事实在源文件里的行区间，如 `节「实习经历」L17-L21`。
- **数字级**（`量化值[].定位`）：该数字在源文件哪一行，如 `L19`。

两者是两回事，不可互相覆盖。`已溯源=false` 表示数字在源文本定位不到，进 `无源量化值` 字段。无源判定不看状态：即使状态已被「主源冲突」或「需OCR人工录入」占用，无源数字仍照写，队列的无源区也按该字段取数——同一条目可能同时出现在冲突区与无源区。

## 量化值噪声过滤：宁保守勿误杀

量化值过滤只针对已证实的噪声形态：时刻记号与时区偏移、多级章节号、点分串（IP）、文件名序号、列表编号、英文技术名 + 小数版本号。每条过滤都配豁免保住真事实：考试分数（CET-6/IELTS/雅思/托福/GRE/GPA 等）前置豁免，数字后紧贴度量单位的写法保留。

纪律：新增过滤规则必须同步往 `collector/tests/regression_guard.py` 加用例，期望值先用旧版实测对照确认差异来自本次改动；做不到「既去噪又不误杀」时宁可少去，把残留写进 commit message。护栏本体入库（不放 state/），换机器不丢。

## 日期抽取：三重校验

从文件名抽日期时：① 候选段前后不紧邻数字（否则只是雪花 ID 一类长数字串的中段）；② 年份后无分隔符时只认 YYYYMM / YYYYMMDD 紧凑形态；③ 月 1–12、日不超该月真实天数（calendar 校验，拒 2026-02-30）。全不合法则时间字段留空，绝不硬塞一个不可能的日期。

## 模板识别：双阈值

文件名带「模板/demo/template/占位」只是初筛。文本文件还要求正文占位符（X.X、20XX、{{}}、Lorem ipsum、example@ 等）同时达到命中数与密度双阈值，才判为「等着被填空的模板」；二进制只认强特征文件名。这样「用模板做的真汇报」「模板选型执行说明」一类真成果不会被误杀。判不准时一律放行（fail-open）。

## 状态机与人工核验闭环

| 状态 | 含义 | 谁能改 |
|---|---|---|
| 待核验 | 事实与证据齐备，等人过目 | 人工核验后置已核验 |
| 已核验 | 人工确认事实与数字无误 | 只能由人置，采集器永不自动置 |
| 主源冲突 | 同一事实多源表述不一致且未裁决 | 人工裁决后按场景归类改待核验 |
| 无源待确认 | 有数字定位不到，或整条无文件证据 | 人工补证后改待核验；补不到就删条目 |
| 需OCR人工录入 | 二进制只登记了路径与元信息 | 人工录入后改待核验 |

闭环三段：全量扫描 → 会话增量 hook → 人工核验转正。采集器只负责把事实连同证据搬进来；转正的唯一入口是人在 `待核验队列.md` 底部裁决区留结论（只追加，生成器不覆盖），然后才允许改状态。

## 多源场景归类与配置化警示

同一事实有多个主源（如多份简历）时，采集器只标 `主源冲突组`、不选边。人工裁决把「按场景并存」写进 sources.json：`主源冲突文件` 列成员，`简历场景映射` 定归属场景，`主源裁决` 存裁决依据原文。裁决只定主源归属，不裁决内容真伪——条目状态回到「待核验」，仍在队列里等人过目。

安全阀：文件在 `主源冲突文件` 里但 `简历场景映射` 漏配时，仍标「主源冲突」，避免映射漏配导致冲突标记被静默丢掉。

`场景警示规则` 是源配置里的数组：`场景含` 匹配场景标签、`文本匹配` 正则（忽略大小写）命中名称/成果时写入 `警示` 文案；坏正则跳过，无规则不打。典型用法：保研场景的排名/成绩类条目禁止流入求职简历表述；语言考试成绩不配进规则，因为两个场景都写。

## hook fail-open：三道防线

1. `json.load` 外层 `except Exception`——不止 ValueError/OSError；
2. `isinstance(data, dict)` 守卫——stdin 是合法 JSON 但为数组/字符串/数字时当空输入处理；
3. `__main__` 兜底 try/except——任何未预料异常也只 exit 0。

写盘边界：日志目录由脚本自身位置推导，不使用 cwd，无论 IDE 从哪个工作目录调起都只写进本仓库内。transcript 只读不写，只做字节/行级轻量统计，不假设其 JSON 结构。

## 隐私默认

发布版 `.gitignore` 排除全部采集产物与运行时状态（`中台数据/`、`待核验队列.md`、`采集日志.md`、`collector/state/`、`.qoder/settings.local.json`）。复用者 clone 后跑起来，自己的真实个人数据默认不会被 git 追踪。仓库本身只含引擎、配置模板、合成示例与文档。
